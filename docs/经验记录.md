# 经验记录

## 2026-10-22　多窗口后微软拼音候选框钉在左上角

症状：开两扇窗口来回切换后，打中文时微软拼音弹出它自己画的组字窗（白底带图标），候选条钉在窗口左上角，不跟随光标；偶发上屏重复。单窗口时代从未出现，`efa944d`（多窗口）之后高频出现。

**排查走的弯路**：一开始以为是前端上报的光标位置不对，在 `frontend/src/terminal/ime.ts` 加插桩验证——textarea 位置全程正确稳定，但 IME 根本不读。前端定位的修法（冻结锚点、start 时摆位、focus 时挪 1px 强制重报）全部无效。教训：**IME 自绘兜底 = TSF 没拿到应用的文本上下文，和应用把位置摆得多对无关**，先验证 IME 有没有读，再调定位。

**根因**：`main.go` 没设 `WebviewUserDataPath`，两扇窗口共用同一个 WebView2 用户数据目录，也就共用同一个 `msedgewebview2.exe` 浏览器进程。Chromium 的输入法桥（TSF bridge）是浏览器进程 UI 线程里的单例，两窗切换时登记的焦点文本客户端可能没跟着切，TSF 对新窗口只有空上下文，微软拼音拿不到 caret 位置就自绘钉 (0,0)。实机验证：两个 `TermPilot.exe` 进程只对应一个 WebView2 浏览器主进程（`Get-CimInstance Win32_Process` 查 `msedgewebview2.exe`，没有 `--type=` 的是主进程）。

**修法**（`9fe071f` 首版，后修正）：`main.go` 设置 `Windows.WebviewUserDataPath = app.WebviewDataDir()`。按**实际占用**抢锁分配目录：先抢基础目录 `%AppData%\<exe名>`（槽位 0，抢到即首个窗口，老用户的 localStorage 不丢）；抢不到说明已有窗口在跑，再抢 `windows\1`、`windows\2`… 槽位目录。锁用 `LockFileEx`，随进程退出释放，崩溃不留死槽。每窗一个浏览器进程，输入法各管各的。

**首版的坑**：`9fe071f` 当时靠启动参数 `--extra-window` 判断要不要隔离，而这个参数只有应用内"新窗口"按钮会带；`a1d3aaf` 后来删了按钮，修复就静默失效了——双击 exe、任务栏、右键菜单开的第二扇窗全部回落到共用目录。**判断"要不要隔离"不能看入口参数，要看实际占用**。

注意之前用 `WEBVIEW2_USER_DATA_FOLDER` 环境变量的实验无效记录不作数——没验证过进程真的隔离了；后来生效的是 `WebviewUserDataPath` 选项显式传目录（go-webview2 v1.0.22 `chromium.go:167` 总会显式传数据目录，环境变量和显式参数谁优先没验证过）。

代价：每扇窗口多一个浏览器进程（几十 MB 内存）；新窗口的 localStorage 独立（外观缓存等首帧默认值，可接受）。

**备用排查手段**（以后若再复发）：先分清形态——正常是 xterm 画的黑底组字框（`.composition-view`）+ 候选条跟随光标；异常是微软拼音自绘的白底组字窗（带绿图标）钉左上，自绘 = IME 没读应用上报的 caret，调前端定位没用。验证进程隔离：`Get-CimInstance Win32_Process` 查没有 `--type=` 的 `msedgewebview2.exe`，每扇窗应对应一个浏览器主进程、各自的 `--user-data-dir`。仍复发再试：微软拼音设置里的"使用以前版本的微软拼音"兼容开关；换输入法对照（坐实是否微软拼音特有）；写一个只有 textarea 的 Wails 双窗口最小复现，去 MicrosoftEdge/WebView2Feedback 报 issue。前端插桩点（`frontend/src/terminal/ime.ts`）：compositionstart/update/end 序列、textarea 位置变化、window focus/blur，用 console.log（DevTools 默认不显示 console.debug）。

## 2026-10-22　密钥登录开新会话时闪一下黑窗

症状：下拉开新会话时偶尔有个控制台窗口一闪而过，像弹权限确认。看着随机，实测规律稳定：**密钥登录的主机、开第一个连接时**必闪；密码登录不闪，已有连接可复用（连接池 `internal/terminal/ssh.go` 的 `pool.Acquire`）时不闪。

**根因**：`internal/sshx/keys.go` 的 `identityFilesFor` 调 `ssh -G` 问系统 ssh 用哪些私钥（`3ec815d` 引入），是全项目唯一没设 `HideWindow` 的控制台子进程。TermPilot 是 GUI 程序没有控制台，Windows 就给 `ssh.exe` 新配一个；`ssh -G` 几十毫秒退出去，窗口闪一下。

**修法**：拆出 `cmd` 调同包已有的 `hideWindow(cmd)` 再 `.Output()`。顺带把 `sshx.hideWindow`、`app.hideConsole`（powershell 各处）、`shells_windows.go` 的 `where.exe` 三处都加上 `CreationFlags: CREATE_NO_WINDOW`。

教训两条：

1. **GUI 程序起控制台子进程，每一处都要藏窗口**，漏一处就闪。排查时用 `Win32_ProcessStartTrace` 抓进程（看闪的那一刻谁的父进程是 TermPilot.exe）比猜快。
2. **`HideWindow` 只是 `SW_HIDE`，不等于没有窗口**：Win11 默认终端应用设成 Windows Terminal 时新控制台被它接管，`SW_HIDE` 可能失效——这解释了"同样的操作有的电脑闪有的不闪"。只读输出、不需要交互的子进程一律用 `CREATE_NO_WINDOW`，让系统根本不配控制台。`startDetached` 的 `DETACHED_PROCESS` 是起 GUI 的 TermPilot 自己，不受影响。

## 2026-10-22　本机 wails CLI 版本会悄悄改 go.mod

本机 wails CLI 是 v2.12.0、项目 go.mod 用 v2.16.0 时，每次 `wails dev` / `wails build` 都会把 go.mod 降级回 v2.12.0（git status 里那个莫名其妙的 go.mod 改动就是它）。升级解决：`go install github.com/wailsapp/wails/v2/cmd/wails@v2.16.0`。CLI 和库版本要一起看。

## 2026-10-18　全屏程序的滚动条和背景块

只在 Windows 本机终端里跑 Pi 时看到。两处都已修好，在 Pi 里确认过：滚动条竖线不断，用户消息和代码块有背景。

### 滚动条某一行少一列

Pi 先按自己的列宽把一行切到最右一列，再把轨道 `│`、滑块 `┃`（悬停时换成 `█`）插进去。带 `U+FE0F`（emoji 样式选择符）的字符，Pi 算 2 格，当时 xterm 用的 Unicode 11 宽度表算 1 格（底字符 1 格，选择符 0 宽）。`⚠️`、`✔️`、`ℹ️`、`☑️`、`❤️` 都是这样；`✨`、`🔧`、方框线和普通 ASCII 两边一致。

某一行里只要有一个这种字符，竖线就落到左边一格。往格子外多画 1 像素对不上，因为差的是整列，不是像素。

无界面 xterm 写入 `a⚠️b✔️c✨d|` 核对过：Pi 认为 `|` 在第 10 列，Unicode 11 排在第 8 列，`@xterm/addon-unicode-graphemes@0.4.0` 排在第 10 列。

`frontend/src/terminal/TerminalPool.ts` 已换成这个插件，宽度版本是 `15-graphemes`。它按 Unicode 15 的字素簇算，ZWJ 拼接的组合 emoji 也算在内。SSH 会话没有 ConPTY 再排一遍宽度，同样受益。

### Pi 的用户消息和代码块没有背景

Pi 的 system 主题自己不猜颜色。启动时问终端要前景色（OSC 10）、背景色（OSC 11）和 16 色调色板（OSC 4），最后用设备属性查询（DA1，`CSI c`）当作这一轮的结束标记。18 个颜色到齐，或收到 DA1 应答，这一轮就结束。什么都没拿到时，面板背景留空。

xterm 会用当前主题回答这些查询。Windows 自带的 ConPTY（`kernel32` 的 `CreatePseudoConsole`）把查询吃掉，并抢先回了 DA1（`CSI ?61;6;7;21;22;23;24;28;32;42 c`）。Pi 收到结束标记时颜色是空的，背景块就不画。晚到的颜色补不进已经结束的这一轮。Windows 终端正常，是因为它用的是新版 OpenConsole，不是系统自带的 conhost。

当时的依赖 `github.com/UserExistsError/conpty` v0.1.4 把 `kernel32.dll` 写死了，没法换 DLL。现已改成随程序带的官方包 `Microsoft.Windows.Console.ConPTY` 1.25.260930003（MIT）：

- `scripts/prebuild.mjs` 下载这个包，解出 x64 和 arm64 的 `conpty.dll` 与 `OpenConsole.exe`。版本号要和 `internal/terminal/conpty_setup_windows.go` 里的 `bundledConptyVersion` 一致。
- `internal/terminal` 按当前架构内嵌这两个文件。第一次启动释放到 `%APPDATA%\TermPilot\conpty\<版本>\`，再加载。`conpty.dll` 从自己所在的目录找 `OpenConsole.exe`，两个文件必须放在一起。
- `internal/winconpty/conpty.go` 改编自原来的依赖。创建、调整大小、关闭从这份 DLL 加载；加载失败时退回 `kernel32`，本机终端仍能开。属性列表的两个函数只在 `kernel32` 里，继续用它。

新版 OpenConsole 启动时会自己先发一次 DA1，xterm 会回答，不用额外处理。其他要查询终端颜色的程序也走得通。

用真实 ConPTY 起子进程发过同样的背景色查询：系统那份下，宿主一个查询都没收到；换成这份 DLL 后，查询转到宿主，回答回到子进程。`TestBundledConptyForwardsBackgroundQuery` 锁着这件事。
