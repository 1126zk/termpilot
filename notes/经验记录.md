# 经验记录

## 2026-10-22　多窗口后微软拼音候选框钉在左上角

症状：开两扇窗口来回切换后，打中文时微软拼音弹出它自己画的组字窗（白底带图标），候选条钉在窗口左上角，不跟随光标；偶发上屏重复。单窗口时代从未出现，`efa944d`（多窗口）之后高频出现。

**排查走的弯路**：一开始以为是前端上报的光标位置不对，在 `frontend/src/terminal/ime.ts` 加插桩验证——textarea 位置全程正确稳定，但 IME 根本不读。前端定位的修法（冻结锚点、start 时摆位、focus 时挪 1px 强制重报）全部无效。教训：**IME 自绘兜底 = TSF 没拿到应用的文本上下文，和应用把位置摆得多对无关**，先验证 IME 有没有读，再调定位。

**根因**：`main.go` 没设 `WebviewUserDataPath`，两扇窗口共用同一个 WebView2 用户数据目录，也就共用同一个 `msedgewebview2.exe` 浏览器进程。Chromium 的输入法桥（TSF bridge）是浏览器进程 UI 线程里的单例，两窗切换时登记的焦点文本客户端可能没跟着切，TSF 对新窗口只有空上下文，微软拼音拿不到 caret 位置就自绘钉 (0,0)。实机验证：两个 `TermPilot.exe` 进程只对应一个 WebView2 浏览器主进程（`Get-CimInstance Win32_Process` 查 `msedgewebview2.exe`，没有 `--type=` 的是主进程）。

**修法**（`9fe071f` 首版，后修正）：`main.go` 设置 `Windows.WebviewUserDataPath = app.WebviewDataDir()`。按**实际占用**抢锁分配目录：先抢基础目录 `%AppData%\<exe名>`（槽位 0，抢到即首个窗口，老用户的 localStorage 不丢）；抢不到说明已有窗口在跑，再抢 `windows\1`、`windows\2`… 槽位目录。锁用 `LockFileEx`，随进程退出释放，崩溃不留死槽。每窗一个浏览器进程，输入法各管各的。

**首版的坑**：`9fe071f` 当时靠启动参数 `--extra-window` 判断要不要隔离，而这个参数只有应用内"新窗口"按钮会带；`a1d3aaf` 后来删了按钮，修复就静默失效了——双击 exe、任务栏、右键菜单开的第二扇窗全部回落到共用目录。**判断"要不要隔离"不能看入口参数，要看实际占用**。

注意之前用 `WEBVIEW2_USER_DATA_FOLDER` 环境变量的实验无效记录不作数——没验证过进程真的隔离了；后来生效的是 `WebviewUserDataPath` 选项显式传目录（go-webview2 v1.0.22 `chromium.go:167` 总会显式传数据目录，环境变量和显式参数谁优先没验证过）。

代价：每扇窗口多一个浏览器进程（几十 MB 内存）；新窗口的 localStorage 独立（外观缓存等首帧默认值，可接受）。

**备用排查手段**（以后若再复发）：先分清形态——正常是 xterm 画的黑底组字框（`.composition-view`）+ 候选条跟随光标；异常是微软拼音自绘的白底组字窗（带绿图标）钉左上，自绘 = IME 没读应用上报的 caret，调前端定位没用。验证进程隔离：`Get-CimInstance Win32_Process` 查没有 `--type=` 的 `msedgewebview2.exe`，每扇窗应对应一个浏览器主进程、各自的 `--user-data-dir`。仍复发再试：微软拼音设置里的"使用以前版本的微软拼音"兼容开关；换输入法对照（坐实是否微软拼音特有）；写一个只有 textarea 的 Wails 双窗口最小复现，去 MicrosoftEdge/WebView2Feedback 报 issue。前端插桩点（`frontend/src/terminal/ime.ts`）：compositionstart/update/end 序列、textarea 位置变化、window focus/blur，用 console.log（DevTools 默认不显示 console.debug）。

## 2026-10-22　密钥登录开新会话时闪一下黑窗

症状：下拉开新会话时偶尔有个控制台窗口一闪而过，像弹权限确认。看着随机，实测规律稳定：**密钥登录的主机、开第一个连接时**必闪；密码登录不闪，已有连接可复用（连接池 `internal/terminal/ssh.go` 的 `pool.Acquire`）时不闪。

**根因**：`internal/sshx/keys.go` 的 `identityFilesFor` 调 `ssh -G` 问系统 ssh 用哪些私钥（`3ec815d` 引入），是全项目唯一没设 `HideWindow` 的控制台子进程。TermPilot 是 GUI 程序没有控制台，Windows 就给 `ssh.exe` 新配一个；`ssh -G` 几十毫秒退出去，窗口闪一下。

**修法**：拆出 `cmd` 调同包已有的 `hideWindow(cmd)` 再 `.Output()`。顺带把 `sshx.hideWindow`、`app.hideConsole`（powershell 各处）、`shells_windows.go` 的 `where.exe` 三处都加上 `CreationFlags: CREATE_NO_WINDOW`。

教训两条：

1. **GUI 程序起控制台子进程，每一处都要藏窗口**，漏一处就闪。排查时用 `Win32_ProcessStartTrace` 抓进程（看闪的那一刻谁的父进程是 TermPilot.exe）比猜快。
2. **`HideWindow` 只是 `SW_HIDE`，不等于没有窗口**：Win11 默认终端应用设成 Windows Terminal 时新控制台被它接管，`SW_HIDE` 可能失效——这解释了"同样的操作有的电脑闪有的不闪"。只读输出、不需要交互的子进程一律用 `CREATE_NO_WINDOW`，让系统根本不配控制台。`startDetached` 的 `DETACHED_PROCESS` 是起 GUI 的 TermPilot 自己，不受影响。

## 2026-10-18　全屏程序的滚动条和背景块

只在 Windows 本机终端里跑 Pi 时看到。两处都已修好，在 Pi 里确认过：滚动条竖线不断，用户消息和代码块有背景。

### 滚动条某一行少一列

Pi 先按自己的列宽把一行切到最右一列，再把轨道 `│`、滑块 `┃`（悬停时换成 `█`）插进去。带 `U+FE0F`（emoji 样式选择符）的字符，Pi 算 2 格，当时 xterm 用的 Unicode 11 宽度表算 1 格（底字符 1 格，选择符 0 宽）。`⚠️`、`✔️`、`ℹ️`、`☑️`、`❤️` 都是这样；`✨`、`🔧`、方框线和普通 ASCII 两边一致。

某一行里只要有一个这种字符，竖线就落到左边一格。往格子外多画 1 像素对不上，因为差的是整列，不是像素。

无界面 xterm 写入 `a⚠️b✔️c✨d|` 核对过：Pi 认为 `|` 在第 10 列，Unicode 11 排在第 8 列，`@xterm/addon-unicode-graphemes@0.4.0` 排在第 10 列。

`frontend/src/terminal/TerminalPool.ts` 已换成这个插件，宽度版本是 `15-graphemes`。它按 Unicode 15 的字素簇算，ZWJ 拼接的组合 emoji 也算在内。SSH 会话没有 ConPTY 再排一遍宽度，同样受益。

### Pi 的用户消息和代码块没有背景

Pi 的 system 主题自己不猜颜色。启动时问终端要前景色（OSC 10）、背景色（OSC 11）和 16 色调色板（OSC 4），最后用设备属性查询（DA1，`CSI c`）当作这一轮的结束标记。18 个颜色到齐，或收到 DA1 应答，这一轮就结束。什么都没拿到时，面板背景留空。

xterm 会用当前主题回答这些查询。Windows 自带的 ConPTY（`kernel32` 的 `CreatePseudoConsole`）把查询吃掉，并抢先回了 DA1（`CSI ?61;6;7;21;22;23;24;28;32;42 c`）。Pi 收到结束标记时颜色是空的，背景块就不画。晚到的颜色补不进已经结束的这一轮。Windows 终端正常，是因为它用的是新版 OpenConsole，不是系统自带的 conhost。

当时的依赖 `github.com/UserExistsError/conpty` v0.1.4 把 `kernel32.dll` 写死了，没法换 DLL。现已改成随程序带的官方包 `Microsoft.Windows.Console.ConPTY` 1.25.260930003（MIT）：

- `scripts/prebuild.mjs` 下载这个包，解出 x64 和 arm64 的 `conpty.dll` 与 `OpenConsole.exe`。版本号要和 `internal/terminal/conpty_setup_windows.go` 里的 `bundledConptyVersion` 一致。
- `internal/terminal` 按当前架构内嵌这两个文件。第一次启动释放到 `%APPDATA%\TermPilot\conpty\<版本>\`，再加载。`conpty.dll` 从自己所在的目录找 `OpenConsole.exe`，两个文件必须放在一起。
- `internal/winconpty/conpty.go` 改编自原来的依赖。创建、调整大小、关闭从这份 DLL 加载；加载失败时退回 `kernel32`，本机终端仍能开。属性列表的两个函数只在 `kernel32` 里，继续用它。

新版 OpenConsole 启动时会自己先发一次 DA1，xterm 会回答，不用额外处理。其他要查询终端颜色的程序也走得通。

用真实 ConPTY 起子进程发过同样的背景色查询：系统那份下，宿主一个查询都没收到；换成这份 DLL 后，查询转到宿主，回答回到子进程。`TestBundledConptyForwardsBackgroundQuery` 锁着这件事。

## 2026-10-25　网站页签拖拽排序连踩两坑

症状：给网站页的 nginx/caddy 页签加拖拽排序，第一版拖起来页签"飞了"（截图里像多出一个页签）；换方案后第二版两个页签叠在一起。

**坑一：HTML5 原生拖拽不适合做排序。** 第一版图省事用了 `draggable` 属性 + `onDragStart/onDrop`，浏览器会自动生成一个跟随鼠标的半透明残影（drag ghost），截图里"第三个 caddy"就是它——不是数据错了，是残影乱飞。而且原生拖拽的触发、落点高亮、位移全要手写，手感跟应用里已有的拖拽完全两套。**教训：项目里已有 `frontend/src/components/flip.ts` 这套公共件（pointer 拖拽 + FLIP 让位，TabBar 标签条和 + 菜单都在用），做拖拽排序先找它，别自己起炉灶。**

**坑二：拖动中的交换判定用了旧快照。** 换到 flip 方案后，`onMove` 里做交换判定的闭包抓的是 pointerdown 那一刻渲染的 `webTabs` state。第一次交换后 state 更新了，但后续 move 回调还拿旧数组算位置，于是换过去又换回来，两个页签叠在一起。TabBar 早就踩过这个坑，用 `menuOrderRef` 拿最新顺序——照抄即可：**拖动期间的判定数据一律走 ref（随 setState 同步写），不能信闭包里的 state。**

最终形态（`OpsPanel.tsx` WebSection）：pointer 拖拽跟手、钳制在首尾之间，越过对方中点即交换，对方 FLIP 160ms 让位，4px 阈值内算点击；顺序写 `localStorage`，每次打开默认选中排第一个的页签。

## 2026-10-25　拉镜像卡死的连环坑

症状：网站页一键安装 nginx/caddy 反复卡死，日志停在 Pull complete / Pulling fs layer 不动，面板永远"安装中"。

**根因一（网络）**：社区公益镜像源（1ms.run 等）时好时坏，docker 按 registry-mirrors 顺序试，某个源挂住就傻等不换。对比：1Panel 用自己的商业源（docker.1panel.live），所以人家装什么都快。**教训：镜像源质量是装得动的前提，默认源列表要用经过验证的（1Panel 那组），并且让用户能在面板上自己管。**

**根因二（超时失效）**：Exec 超时到点只 session.Close()，而 sshd 在子进程活着时故意推迟回 CLOSE，本地读协程永远收不到 EOF，copyWg.Wait() 死等——超时形同虚设。修法：先 SIGKILL 远端子进程再 Close，读协程最多再陪等 2 秒强制返回。同时调用方必须查 res.TimedOut，否则超时会被当成成功。

**修法链**：pull 套 timeout 快速失败；标准名拉不动按 daemon.json 的源逐个显式前缀重试（手动救场的自动化）；daemon.json 不再由安装脚本生成，改在 Docker 页"镜像加速"小节让用户自己增删（reload 热生效）。

**附带两个小坑**：cat 采集没有换行结尾的文件会把 #TP-END# 标记粘到最后一行（写入时补 \n + 采集时补 echo）；useState 写在 if 提前 return 后面会直接白屏（钩子数量不一致）。

## 2026-11-02　终端右侧双滚动条

症状：终端右侧除了 xterm 自绘的细滚动条，还会冒出一条带上下箭头的原生滚动条。滑块很长、停在顶部，不跟随回滚位置。只在**窗口缩小到一定程度后**再滚动才出现，放大不出现；滚动时露出，停下后隐藏（WebView2 的 Fluent 滚动条行为）。

**根因**：`frontend/src/index.css` 为了挡住组字条把终端横向滚走，给 `.xterm-screen`、`.xterm-scrollable-element` 设了 `overflow-x: hidden`。CSS 规定一个方向是 `hidden`/`auto`/`scroll` 时，另一方向的 `visible` 会被算成 `auto`，于是 `.xterm-screen` 变成了 `overflow-y: auto`。窗口缩小时 screen 高度立刻变小，里面的内容还是旧高度（实测 scrollHeight 738 vs clientHeight 540），溢出就出了原生竖条。

**修法**：这两个元素改用 `overflow-x: clip`。`clip` 不会把另一方向改成 `auto`，而且连程序触发的滚动也禁止，挡组字条的效果不变。`.xterm-viewport` 本来就是 `overflow-y: scroll`，保留 `hidden`。

**弯路**：一开始的调查报告认定是 `.xterm-viewport` 的原生条和 xterm 自绘条叠在一起，先后两次去藏 viewport 的滚动条都无效。原因是只读代码猜元素，没在运行中的窗口里确认到底是谁在滚。另外两点也误导过判断：

- xterm 6 的自绘条不支持箭头（开 `verticalHasArrows` 会直接抛错），**带箭头的一定是原生滚动条**。
- 全局 `*` 设了 `scrollbar-width`/`scrollbar-color`，Chromium 121+ 下这会让所有 `::-webkit-scrollbar` 规则失效，`index.css` 里给 viewport 写的那套 webkit 样式其实一直没生效。

**教训**：

1. 单轴设 `overflow-x: hidden` 会顺带打开另一轴的滚动。只想裁掉一个方向时用 `clip`。
2. 视觉问题先在 DevTools（`wails dev` 下 Ctrl+Shift+F12）里列出真正有滚动条的元素，再动手改。可以在 Console 里筛出 `overflowY` 为 `auto`/`scroll` 且 `scrollHeight > clientHeight` 的元素，看 class 和位置。
3. 复现条件要问全：这次关键的触发条件是"缩小窗口"，`seq 1 1000` 直接滚是复现不出来的。

## 2026-11-25　文件条拖标签又飞又闪，右边多一个箭头

症状：标签内分栏的文件条上拖终端，标签叠在一起乱飞，下面的终端跟着闪；只有两个标签、右边还有大片空白时，最右边仍出现一个向右的箭头。顶栏标签拖拽以前修过（`138cee3`：拖动不切换焦点；`ec5ba40`：右边空着时不收起），这次在文件条上又出现。

**为什么修过还会再出现。** 那两条约束只写在 `TabBar.tsx` 里，没有变成拖拽的共同规则。文件条（`EditorTabBar.tsx`）后来自己接了 `flip.ts`，又为了加号紧挨标签，把条子从顶栏那种撑满宽度改成「刚好包住内容」。两处一改，旧坑原样回来：

1. **拖动过程中改了布局。** 每移动一下就更新正在看的终端（`primaryView` / `focus`），一侧暂时没有终端就当场收起分栏。标签的 `offsetLeft` 跟着变，下一次命中测试判到另一侧，顺序换过去又换回来，FLIP 让位和跟手位移叠在一起，看起来就是飞、闪。竖线只有 1px，来回越过中点尤其容易弹。
2. **用「包住内容」的滚动盒子量溢出。** `width: fit-content` / `max-content` 再加 `overflow-x: auto`，`scrollWidth` 会比 `clientWidth` 大出一点点，两个标签也判定为溢出，于是画出左右箭头。箭头一插进布局，坐标再变一次，拖动更抖。

**修法**（`EditorTabBar.tsx`、`useAppStore.ts` 的 `reorderSessionStrip` / `settleSessionStrip`、`App.tsx` 的 `SessionSplitPane`）：

- 拖动中只改标签顺序和竖线左右的归属。不换正在看的终端，不收起内容分栏（`stripDragTermId` 挡住 `secondary` 为空时的收起），也不在拖动中途改溢出状态。
- 越过竖线要多过一段（约 16px）才换边，避免在 1px 竖线上来回弹。
- 松手再结算：某一侧没有终端才收起，并让左右各自对上还在那一侧的终端。
- 溢出按「标签行的内容宽度」和「槽位减去加号之后的可用宽度」比。放得下时条子用 `w-max`、`overflow-x: hidden`，不出现箭头；真的放不下才滚动并显示箭头。

**教训**：顶栏已经验证过的拖拽约束，新的一条标签条必须照用，不能只复用 `flip.ts` 的跟手和让位。两条写死：

1. 指针没松开之前，只许挪被拖的那一项和让位动画。不许切换正在显示的内容，不许收起分栏，不许插入会改变坐标的按钮。
2. 不要对一个宽度刚好等于内容的盒子读 `scrollWidth - clientWidth` 来决定要不要滚动箭头。那种盒子再开 `overflow: auto`，几乎总会被判成溢出。

## 2026-11-27　笔记图片行高亮来回跳，图片前后按 Backspace 没反应

症状：笔记里贴了图片，光标停在图片行时，当前行高亮有时在图片上、有时在图片下一行，来回跳。图片下一行开头按 Backspace 没反应；有时那一行的文字被并进图片行，行号也没了。

**根因一（光标位置有歧义）**：粘贴图片时 `insertImage` 把 `<img><br>` 插进当前行的 `<div>` 里，图片和下一行挤在同一个块里。图片是块级的，紧挨图片后面（`<br>` 前面）这同一个 DOM 位置，Chrome 按 caret affinity 有时把光标画在图片右上角，有时画在下一行开头。Selection API 读不出 affinity，按 DOM 顺序算行号（`markIndex`）的结果是固定的，画出来的位置却会变。

**根因二（Chrome 删不动块级图片）**：图片单独成块后，前后按 Backspace / Delete，Chrome 自带的合并段落要么什么都不做，要么把下一行文字并进图片块。并进来的文字会被 Chrome 包进 `<span>`，`readLineMarks` 不进行内元素，这一行就量不到、没有行号，高亮也一直停在图片行。

**弯路**：前一轮改法改成「量光标画在哪一行」（`caretLineTop`）。affinity 照样量不出来；量不到时往 DOM 里插零宽 `<span>` 去量，再 `removeAllRanges/addRange` 把选区放回去，而重设选区会把 affinity 重置、光标挪走，量一次就跳一次，越改越乱。为了不让自己插的节点触发重算，还临时屏蔽了 MutationObserver，会漏掉用户自己打字引起的变化。

**修法**（`frontend/src/components/tools/NotesTool.tsx`）：

- `isolateImage` 把每张图片拆成独占一行的 `<div><img></div>`，前后的内容拆到各自的块，紧跟图片的 `<br>` 去掉。粘贴走 `insertImage` 调它，光标放到下一行；加载走 `toEditorHtml` 调它，旧格式的笔记也会被整理好。
- 当前行回到按 DOM 顺序判断（`markIndex`），删掉 `caretLineTop`、零宽字符测量和 MutationObserver 的屏蔽。
- 图片前后的 Backspace / Delete 由 `deleteNearImage` 自己处理：光标在图片行删整张图；下一行开头按 Backspace 删上面的图；上一行末尾按 Delete 删下面的图；已经并进图片块的文字，光标紧挨图片时按 Backspace 删这张图。其他位置不拦。
- `readLineMarks` 进 `<span>` 等行内元素里量行。

代价：这些删除直接改 DOM，Ctrl+Z 撤销不了。

**教训**：

1. contentEditable 里，一个 DOM 位置画在哪，要看浏览器的 affinity，而 Selection API 读不到它。光标位置有歧义时，改 DOM 结构让歧义不存在（块级图片独占一个块），不要去量光标画在哪。
2. 测量时不要为了量而改 DOM、重设选区。重设选区本身就会让光标换位置，量的结果和用户看到的永远对不上。
3. 块级图片前后的删除别指望浏览器自带行为，直接拦键处理。
4. 量行号要走进行内元素。Chrome 合并行、粘贴带样式的文字都会生成 `<span>`。
